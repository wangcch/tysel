> 智能体应获得完成任务所需的权限，而不是其进程能够访问的所有资源。

传统应用安全通常从身份开始：验证调用方、授权请求，并保护服务的外部访问边界。智能体软件在这道边界内部增加了一个问题：程序开始自行决定下一步操作后，究竟允许它做什么？

智能体可以连续执行一系列操作，因此一次错误的影响也可能随之扩大。它可能读取不受信任的指令、动态选择工具、调用模型、失败后重试、等待人工处理，并在数小时后继续。如果进程可以使用部署环境中的所有凭据、访问所有主机、数据库和文件，提示词注入或普通编程错误都会造成更严重的后果。

在 Tysel 中，应用需要明确声明所需的宿主权限。对于由清单控制的资源，应用必须先声明访问需求，再接受部署策略和执行配置等限制。声明本身并不等于获得授权。

本文所说的“能力”是 Tysel 公开的宿主操作，并不声称所有 Tysel 代码都在沙箱中运行。`service` 执行配置适用于受信任的第一方代码，并与原生宿主共享进程。Linux `isolated` 执行配置为信任度较低的 JavaScript 增加工作进程边界，但会有意拒绝下文讨论的宿主能力。能力限制和进程隔离是两个独立层次。

## 未声明的权限，默认不授予

新的 Tysel 项目可以包含空权限表：

```toml
[permissions]
```

此时，应用没有访问出站主机、机密信息、Postgres、Redis 或文件系统根目录的清单授权。即使环境变量已经存在，或依赖库试图调用相关功能，也不会自动获得这些权限。

不过，并不是所有宿主功能都通过 `[permissions]` 中的具名条目授权。嵌入式 SQLite 由受信任执行配置控制；持久存储和入站监听器属于宿主管理的基础设施。关键是每项功能的权限来源都必须明确：清单授权、执行配置或宿主部署配置。

只需要少量资源的服务可以请求：

```toml
[permissions]
fetch = ["api.example.com"]
secrets = ["API_TOKEN"]
postgres = ["main:read-only"]
fs_read = ["./prompts"]
fs_write = ["./data/output"]
```

每个字段都要指定具体的资源范围，不能只笼统声明资源类别：

- `fetch` 包含主机名，而非任意 URL 前缀；
- 重定向会再次根据白名单检查；
- `secrets` 包含名称，而非机密信息的值；
- 数据库授权具名且可以只读；
- 文件系统访问限制在固定根目录下；
- 读权限不隐含写权限。

加载清单时会拒绝未知字段、空条目和重复条目。配置带有版本，可以和应用代码一起审查。

## 请求不等于权限

清单只是决策的一层：

```text
manifest request
  ∩ deployment policy
  ∩ execution profile
  ∩ runtime support
  = effective capability
```

这可以防止代码变更授予自身超出环境允许范围的权限。在清单中添加文件系统根目录，无法覆盖禁止文件系统访问的执行配置。导入 Wasm Component 接口，无法绕过拒绝该能力的部署策略。同样，清单无法启用运行时尚未实现的能力。

`service` 执行配置为受信任的第一方代码提供完整宿主能力接口，同时仍要求清单授权。`isolated` 执行配置在单独工作进程中运行 JavaScript，即使清单列出相应能力，也会拒绝面向宿主的网络、数据库、文件系统、LLM 和 WebSocket 能力。在 Linux 上，该工作进程还会应用 Landlock、seccomp、资源限额和尽力而为的 cgroup 强制限制。

实验性的 `component` 执行配置也有相应限制：组件导入的接口、清单声明的根目录和部署策略必须相互匹配。它目前向应用开放的能力范围更小，这是有意作出的限制。

选择执行配置，就是进一步限定应用的权限范围。

## 用引用传递机密信息

清单只声明机密信息的名称，不会把实际值写入构建产物。连接 URL 和机密信息的值仍由部署方管理。

对于 `API_TOKEN` 这类已声明的机密信息，JavaScript 会向宿主请求不透明引用。应用可以将该句柄传给宿主能力，而不会获得明文环境变量值。声明本身不会创建机密信息或为其赋值，也不会授权任何未声明名称。

这可以减少日志、异常信息、序列化或模型上下文造成的意外泄露，但不能免除运维责任：环境变量和提供商凭据仍需得到保护、轮换和基础设施策略约束。

## 让类型提示反映实际权限

修改清单权限后，可以用 `tysel types` 生成与该清单对应的 TypeScript 类型声明：

```sh
tysel types
tysel types --check
```

生成的 `TyselEnv` 只包含项目已声明的能力。调用未获授权的能力时，开发者可以在编辑器或 CI 类型检查中提前发现问题。

类型提示能帮助开发者发现问题，但安全限制仍须在运行时执行。生成的声明不会授予权限，类型中出现的主机名仍需运行时白名单强制检查。最终是否允许操作，仍由原生宿主决定。

这样，类型检查负责提前反馈，宿主负责实际执行权限限制，两者各有职责。

## 检查结果，而不只检查源码

仓库中的 `durable-agent` 示例声明了一项机密信息访问权限，并使用默认 SQLite 持久存储。针对该清单运行仓库工具会得到：

```text
$ tysel inspect --manifest examples/durable-agent/tysel.toml
Application: durable-agent
Profile: service
Entry: src/index.ts
Listen: 127.0.0.1:3000
Logs: json

Capabilities
  Secrets
    OPENAI_API_KEY
  SQLite
    ./data/tysel.db

Denied
  Raw TCP
  Child Process
  FFI
  Dynamic Library
  Environment
```

该输出比“沙箱化智能体”更有审查价值。它展示所选执行配置、清单授权访问的机密信息等资源、由执行配置控制的嵌入式 SQLite 等设施，以及仍不属于应用约定的操作。它没有声称进程本身能够安全运行恶意代码。

## 能力设计会改变审查方式

设想一个读取支持工单、调用 LLM、查询订单并编写建议回复的智能体。传统审查可能关注提示词构造和业务逻辑。能力审查则可以提出具体运维问题：

- 它可以访问哪个模型端点？
- 调用该服务时，使用的是哪一项已声明的机密信息？
- 订单数据库授权是否只读？
- 哪个目录可以保存生成的草稿？
- 工作负载是否需要与宿主共享进程？
- 适用哪些请求、响应、内存、截止时间和并发限额？

这些问题无需追踪智能体的每个可能分支即可回答。清单列出应用请求执行的外部操作及其资源范围；执行配置和部署策略会进一步缩小这一范围。

`tysel inspect` 使实际结果可见：

```sh
tysel check
tysel inspect
```

权限变更后，应在 CI 中运行两条命令。拒绝访问的情况也应与成功调用一样纳入测试：未声明的重定向目标、文件系统穿越、通过只读授权执行修改，以及缺失机密信息，都必须被拒绝，而不能在出错时放行。

## 能力不能替代隔离

能力模型和进程沙箱回答不同的问题。

能力模型规定运行时可以代表应用执行哪些宿主操作。进程隔离限制代码在这些运行时 API 之外能够访问什么。Tysel 的 `service` 执行配置限制能力，但以进程内代码可信为前提，面向第一方代码。Linux `isolated` 执行配置为插件和生成代码增加工作进程边界，同时有意收回面向宿主的能力。

两者都不能替代基础设施控制。生产运维仍需要非 root 身份、出站网络策略、TLS 终止、宿主补丁、机密信息管理，以及数据库和持久存储保护。

要做好纵深防御，首先需要明确每一层负责什么、能防住什么。

## 有权执行，不代表符合用户意图

显式权限可以限制错误的影响范围，但无法证明操作符合用户意图。

如果智能体被允许发送邮件，提示词注入仍可能诱导它发错邮件。能力边界可以限制服务提供商、所用机密信息及相关资源，但产品逻辑仍必须处理确认、策略检查、收件人验证、审计和人工批准。

持久工作流可以记录等待批准的状态和最终决策，避免流程只停留在内存中。但能否在重启后恢复流程，与谁有权批准，仍需分别处理。

## 为长时间运行的智能体设定权限边界

实际目标是明确智能体最多拥有哪些权限，让开发和运维人员能够检查授权、缩小范围，并验证限制是否生效。

对于每项新能力：

1. 从空权限集开始；
2. 添加范围最窄的资源选择器；
3. 选择能够运行工作负载、权限最小的执行配置；
4. 将凭据保留在清单和产物之外；
5. 运行 `tysel check`、`tysel types --check` 和 `tysel inspect`；
6. 在部署环境中测试拒绝路径。

智能体可以决定下一步做什么，但运行时仍应决定它被允许接触什么。
