> 关键问题不是 Tysel 能否取代 Node.js，而是你的工作负载在生产环境中需要哪些能力和保证。

把 Tysel 称为“Node.js 替代品”可以理解。两者在表面上确有重合：都能运行 JavaScript 应用、提供 HTTP 服务、调用远程系统，也都可以在目标机器无需单独安装运行时的情况下交付。

最后一点很重要。现代 Node.js 拥有稳定的[权限模型](https://nodejs.org/api/permissions.html)，可限制文件系统、网络、子进程、工作线程、原生插件、WASI、FFI 和调试器访问。它也拥有[单可执行应用](https://nodejs.org/api/single-executable-applications.html)，可以将脚本嵌入 Node.js 二进制文件。[Bun 可以编译](https://bun.sh/docs/bundler/executables) TypeScript 或 JavaScript 入口、依赖和 Bun 运行时，生成独立可执行文件。Deno 也长期通过其[运行时安全模型](https://docs.deno.com/runtime/fundamentals/security/)明确声明 I/O 权限。

因此，要理解 Tysel 的定位，需要看这些能力如何协同工作。Tysel 用同一套应用模型组织代码、权限、执行配置、恢复机制和发布验证材料。

Tysel 是一个有意收窄范围的运行时，面向服务、任务处理器、MCP 工具、插件和持久智能体。开发者编写 TypeScript，构建工具检查项目配置和兼容性，再将应用与原生 Rust 宿主封装为一个可执行文件。

应用 JavaScript 仍在嵌入式 QuickJS 隔离实例中运行。Tysel **不会**把 TypeScript 编译为原生机器码。“原生”描述的是宿主和交付产物，而不是新的 JavaScript 执行模型。

## 换一种方式组织部署产物

传统 Node.js 部署通常由多项内容组成：

- 一个 Node.js 版本；
- 应用源码或打包结果；
- 生产依赖；
- 包管理器和启动约定；
- 文件系统和环境假设；
- 用于承载这些内容的容器镜像或宿主。

该模型灵活、成熟，适用于非常广泛的应用。它的优势在于环境几乎可以完成服务器进程需要的任何操作。

Tysel 从相反的问题出发：一次部署能否只交付应用、经过验证的配置，以及按这些配置运行应用所需的运行时？

`tysel build` 输出一个包含应用包、清单、源码映射、兼容性元数据和原生运行时的可执行文件。目标机器不需要 Node.js、npm、V8 或 `node_modules`。发布构建还会生成校验和、兼容性结果、聚焦运行时的 SBOM、运行时许可证清单和验证材料索引，作为独立审计伴随文件。

即使可执行文件本身不算小，这种交付方式也能减少运维需要管理的内容：一个可以直接启动的产物、一套可检查的权限模型，以及一个与应用绑定的运行时版本。Node.js SEA、Bun 编译的可执行文件和 `deno compile` 已经解决了运行时安装的大部分问题。Tysel 关注的不只是文件格式：验证、兼容性、打包、权限和发布验证材料都纳入同一套构建检查。

## 权限由宿主管理

在通用服务器运行时中，代码通常通过隐式 API 访问文件系统、进程环境、网络、子进程和原生扩展。容器和操作系统策略可以收紧权限，但应用约定本身不一定逐项列出这些权限。

Tysel 通过原生宿主管理网络、机密信息、数据库、文件系统句柄、限额和持久调度。权限可以来自具名清单授权、所选执行配置或部署方管理的配置。即使某个依赖包默认可以调用 Node.js API，应用也不会因此获得相应的宿主操作权限。

对于清单控制的资源，实际权限不会超出请求范围，还可能进一步缩小：

```text
manifest request
  ∩ deployment policy
  ∩ execution profile
  ∩ runtime support
  = effective capability
```

这种区别对智能体软件尤其重要。智能体可能动态选择操作、处理不受信任的内容、调用模型，并且存活时间远长于一个 HTTP 请求。应用代码不应继承进程环境中恰好存在的所有凭据和文件系统路径。

在 Tysel 中，这些资源需求可以在程序启动前接受审查：`fetch` 可访问的主机名、机密信息名称、数据库授权和文件系统根目录，都需要写入带版本的清单。

完整模型请阅读[默认拒绝：为什么智能体需要显式能力](/blog/capability-by-default)。

## 明确限定兼容范围

Tysel 支持 TypeScript、符合其兼容性约定的 npm 包、Fetch 风格 HTTP，以及一组满足这些场景需求的 Web 标准全局对象。它不承诺支持完整的 Node.js API。

Node.js 内置模块、原生插件、子进程、动态库和任意隐式操作系统访问都不属于 Tysel 应用模型。有些 npm 包打包后可以工作；另一些依赖 Node 特有行为，会被分类为不兼容或未知。兼容性分析为发布准入提供判断依据，不能替代应用测试。

这是一项有意作出的设计取舍：限制兼容范围，才能明确应用可以调用哪些接口、访问哪些资源。

实际工作流因此非常明确：

```sh
tysel check
tysel compat --strict --deny-unknown
tysel inspect
```

`check` 验证项目和能力使用，`compat` 对导入和依赖分类，`inspect` 打印实际权限和限额。兼容性成为发布流程可以检查的内容，而不是只能在部署后发现的问题。

## QuickJS 是实现选择，不是产品本身

QuickJS-ng 为 Tysel 提供适合嵌入、所需集成接口较少的 JavaScript 引擎。这有助于运行时将隔离实例封装进原生宿主，而无需引入通用 Node.js 环境。

但仅将 V8 替换为 QuickJS 并不构成价值主张。单独嵌入一个引擎不会提供能力清单、发布验证材料、执行配置、持久历史、宿主管理的机密信息或构建准入。

Tysel 在引擎之外还提供：

- TypeScript 检查状态报告与应用打包；
- 兼容性分析；
- 受能力控制的宿主；
- 有边界的执行配置；
- 持久操作与恢复；
- 可验证的发布产物集。

QuickJS 支撑这些能力的实现，但引擎本身并不能替代整套应用模型。

## Tysel 的适用场景

如果希望简化部署，并明确限制应用可用的能力，可以在以下场景中评估 Tysel：

- 以单个可执行文件交付的 TypeScript API 或任务处理器；
- 需要审查出站主机和机密信息名称的 MCP 服务器；
- 需要限制并发量和资源用量的定时服务或队列消费服务；
- 能够休眠、等待批准、重试和恢复的持久智能体；
- 应在权限收紧的执行配置下运行的插件或生成函数。

如果应用依赖广泛的 Node.js 兼容性、原生插件、子进程、运行时代码生成，或假设可无限制访问 Node 内部机制的生态框架，那么 Tysel 并不适合。它也不是浏览器运行时、桌面应用框架，不能替代操作系统和网络加固。

## 相似功能，不同约定

比较这些运行时时，需要同时看功能及其使用条件。Node.js、Bun 和 Deno 已具备许多相似能力，Tysel 的区别主要在于如何将它们组合起来：

- **受限 I/O。** Node.js 有稳定的可选权限模型；Deno 在通过命令行参数或交互提示获得授权前拒绝大多数 I/O。Tysel 将能力请求写入带版本清单，再通过部署策略、执行配置和运行时支持收紧。
- **单个可执行文件。** Node.js SEA 嵌入脚本和资源；Bun 将应用包和运行时编译到一起；[`deno compile`](https://docs.deno.com/runtime/reference/cli/compile/) 嵌入程序与运行时。Tysel 将经过验证的应用包嵌入原生宿主，并在发布构建时输出审计伴随文件。
- **威胁模型。** Node 的权限模型保护受信任代码；Deno 的原生库需要单独谨慎处理。Tysel 的 `service` 执行配置同样以进程内代码可信为前提；Linux `isolated` 增加工作进程边界，同时收回宿主能力。
- **高层资源。** 通用运行时提供广泛 API。Tysel 通过清单授权、执行配置和部署配置，为宿主资源提供明确的权限来源。
- **发布记录。** 通用运行时将验证材料和准入策略交给各项目。Tysel 发布构建会输出兼容性、运行时供应链、校验和及验证材料伴随文件。

这种比较不是安全排名。Node.js 明确说明其权限模型是面向受信任代码的“安全带”，而非恶意代码沙箱。Deno 说明原生库会作为机器码在进程内运行。Tysel 自身的 `service` 执行配置也与宿主共享进程，适用于受信任的第一方代码。

Tysel 更具体的区别在于组合：打包、能力请求、执行配置、持久恢复和发布验证材料都属于同一应用模型。该组合是否有价值，取决于工作负载。

## 明确取舍，再选择运行时

Tysel 不试图提供最多的 JavaScript API，而是希望让 TypeScript 应用从开发到上线的各个环节都更容易检查：

```text
write TypeScript
declare authority
verify compatibility
ship one executable
recover durable work
```

如果应用需要 Node.js 的灵活性，就应使用 Node.js。如果你的服务或智能体只需要有限的一组接口，希望显式管理权限，并将应用与运行时一起交付，就可以考虑 Tysel。
