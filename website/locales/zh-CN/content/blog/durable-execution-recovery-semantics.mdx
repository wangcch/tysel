> 恢复是依据已记录历史进行回放，并非延续一个被冻结的 JavaScript 堆。

长时间运行的任务面临的故障场景，与短时请求处理不同。智能体等待批准时，进程可能重启；等待退避重试时，机器可能下线；队列任务处理器可能已完成外部调用，却在记录本地成功状态前崩溃；一次重新部署就可能清除内存中的所有计时器。

让一个 Promise 始终存活在同一 JavaScript 进程中，并不等于持久执行。Tysel 将选定的边界持久化，使处理程序能够重新开始、读取自身历史记录，并从最后一个已完成边界之后继续执行。

要正确使用这一机制，需要先弄清楚它保存了什么，以及恢复时会重新执行什么。

## 带显式边界的普通异步函数

持久处理程序以异步函数编写：

```ts
import type { DurableContext, TyselApp } from "@tysel/types";

const approvalFlow = async (
  ctx: DurableContext,
  input: { orderId: string },
) => {
  const order = await ctx.effect("load-order", () => loadOrder(input.orderId));
  const draft = await ctx.effect("create-draft", () => createDraft(order));

  await ctx.sleep("10m");
  const decision = await ctx.waitForSignal<{ approved: boolean }>("approval");

  return { draft, approved: decision.approved };
};

export default {
  durable: { approvalFlow },
} satisfies TyselApp;
```

语法看起来很熟悉，但 `ctx` 上的调用不是普通辅助函数。这些调用会记录恢复执行所需的历史信息。

| 边界 | 持久化含义 |
| --- | --- |
| `step` | 记录计算结果 |
| `effect` | 记录外部副作用的结果 |
| `sleep` | 持久化唤醒时间并挂起 |
| `waitForSignal` | 挂起，直到指定名称的 JSON 信号被持久化 |
| `retry` | 记录次数受限的重试及其等待时间 |
| `now` | 返回可安全回放的时间 |
| `random` | 返回可安全回放的随机值 |

输入、边界结果、信号和处理程序结果必须可序列化为 JSON。对持久边界的调用必须按顺序 `await`，传入和返回的数据也有大小限制。

## 挂起时会发生什么

当处理程序到达 `sleep` 或 `waitForSignal` 时，Tysel 会持久化挂起状态。计时器运行或等待人工决策期间，无需持续占用 JavaScript 隔离实例。

控制 API 会返回任务 ID，以及已完成或已挂起状态：

```ts
const status = tysel.durable.start("approvalFlow", { orderId: "ord_123" });

tysel.durable.sendSignal(status.taskId, "approval", {
  approved: true,
});
```

信号会追加到持久历史记录中。重启后，运行时可以据此确定：哪个处理程序在等待、哪些边界已经完成，以及所需信号是否已到达。

与进程本地 Promise 或计时器相比，这更适合批准流程、延迟重试、编排和智能体计划。

## 回放从头开始

重启后，Tysel 会依据持久历史记录从第一行开始调用处理程序。它不会反序列化已挂起的 JavaScript 调用栈。

对于每个已完成且有名称的边界，运行时会返回已记录结果，而不会再次执行该操作。已有历史回放完毕后，处理程序才继续执行尚未完成的部分。

以前面的工作流为例：`create-draft` 已完成，任务随后因等待批准而挂起。批准信号持久化后，恢复执行时会依次回放已有记录，再继续处理结果：

```text
start handler
  → load-order: return recorded result
  → create-draft: return recorded result
  → sleep: return recorded completion
  → approval: consume persisted signal
  → execute new code
```

因此，边界名称和顺序是已部署工作流约定的一部分，而不是仅供展示的日志标签。

## 边界之间的代码必须保持确定性

回放会重新运行持久操作之间的普通 JavaScript。对于相同的输入和历史记录，这段代码必须到达相同的持久边界序列。

直接读取的系统时间、未记录的随机值、可变全局状态和无序并发都可能使回放路径发生偏离。因此，持久代码应当：

- 使用 `ctx.now()`，而不是直接读取系统当前时间；
- 使用 `ctx.random()`，而不是未记录的随机值；
- 将外部读取和写入放入已记录边界；
- 按顺序等待持久边界；
- 保持已有边界名称稳定；
- 不要改变进行中任务所用边界的顺序。

边界之间可以进行纯数据转换，只要相同输入始终得到相同结果，就不会破坏回放。影响分支选择的数据库读取即便使用 `SELECT`，也不是纯操作；它应位于已记录的 `effect` 边界内。需要保存确定性计算的结果时，使用 `step`；与外部系统交互时使用 `effect`，包括返回值会影响后续执行的读取操作。

## 副作用提供什么保证

`ctx.effect` 会记录外部副作用的结果。该结果提交到持久历史记录后，回放会直接返回结果，而不会再次发起该外部调用。

这能防止正常恢复期间重复执行已经完成并记录的副作用，却不会凭空创建与任意 API 之间的分布式事务。

以下故障窗口无法避免：

```text
external service commits action
          ↓
process fails before local history commits outcome
```

恢复后，除非外部系统提供识别或查询该操作的方法，否则 Tysel 无法知道外部系统是否已经提交。盲目重试可能会重复产生副作用。

向外部服务发起请求时，应根据持久任务和边界生成稳定的幂等键，并将其传给服务方。如果条件允许，在创建新操作前先用该键查询外部结果。两个独立系统之间的恰好一次行为需要双方配合；运行时无法单方面制造这种保证。

这一区别对于支付、消息、资源创建和模型驱动的工具调用尤其重要。

## 信号是历史记录，而非回调

信号可以在处理程序到达 `waitForSignal` 之前或之后到达。由于信号会被持久化，接收信号时不必恰好有一个监听器在内存中等待。

信号名称和载荷结构是工作流约定的一部分。追加信号前必须验证授权：持有任务 ID 不应自动获得批准、取消或修改工作流的权限。

因此，人工批准至少包含三个层次：

1. 产品逻辑确定需要批准；
2. 接收决策的控制接口先验证调用方身份，再检查其是否有权发送该决策；
3. 持久历史记录保存最终信号，以供回放。

持久存储负责保存决策，应用负责检查发送者的权限。

## 将持久存储作为生产数据管理

SQLite 是默认持久存储：

```toml
[durable]
store = "sqlite"
path = "./data/tysel.db"
```

宿主环境完成相应配置后，运行时也可以使用基于 Postgres 的持久存储。目前，版本 1 清单中的存储配置使用 `sqlite`；要使用 Postgres，需由运维人员在部署配置中指定。

无论选择哪种存储，都应将其视为敏感的运维状态：

- 进行备份并测试恢复；
- 为相对路径设置明确的工作目录；
- 像保护应用数据一样保护它；
- 监控恢复失败、信号处理和调度器健康状态；
- 不要让多个独立调度器操作同一个 SQLite 文件。

历史记录能否可靠保存、部署方式是否正确，直接决定了重启后能否恢复任务。

## 修改已部署工作流

修改工作流代码时，必须考虑正在运行的任务能否用新代码回放已有历史。重命名 `create-draft`、在它之前插入新边界或修改分支条件，可能导致新代码预期的历史记录结构与现有任务不符。

修改之前，先确认现有任务的状态：

- 哪些处理程序版本仍有进行中的实例？
- 它们已经记录了哪些边界名称和序列？
- 新代码能否以确定性方式读取旧历史记录？
- 是否应引入新的工作流名称，而不是修改旧工作流？
- 如何等待旧实例执行完毕，或将它们迁移到新版本？

Tysel 提供回放机制；应用所有者仍需制定工作流版本策略。

## 恢复机制提供的保证

Tysel 持久执行承诺一种明确的模型：

- 已完成的持久边界会被持久化；
- 休眠和等待信号的工作可以释放隔离实例；
- 处理程序中断后会从头开始；
- 回放时复用已记录的边界结果，不再执行对应操作；
- 已有历史回放完毕后，继续执行尚未完成的部分。

它不会保存并还原整个 JavaScript 堆，也无法保证任意非确定性代码都能正确回放。它不会自动与外部服务建立原子事务，传入信号的授权检查也仍由应用负责。

明确这些限制后，才能判断任务在不同故障下会如何恢复。准确的边界标识、信号顺序、重试限制和存储协调都是不断演进的 Durable API 约定的一部分，应在部署前对照当前参考资料进行验证。
